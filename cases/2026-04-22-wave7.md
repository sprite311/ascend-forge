# Wave 7：三个小闭环（--json / tests / pitfall）

## 背景

Wave 6 收尾时列了 5 条候选，按紧急度排了：

1. `wiki_stability.py --json` → `evolve.py` 精确计数（信息丢失）
2. `tests/test_common.py` 覆盖 3 种 YAML 边界（零测试保护）
3. Pitfall "工具名 vs 意图动词冲突" 沉淀（bench 失败共性）
4. `curate.py` 改名 / `evolve.py --steps`（低优先）
5. `adapters/*` 真同步脚本（工作量大）

本 Wave 做 1/2/3——**三个小闭环**，每个都是"已发现但没闭合的问题"。4/5 继续留。

## 做了什么

### 7.1 · `wiki_stability.py --json` + `evolve.py` 精确计数

**问题**：Wave 6 把 `wiki_stability.py` 集成进 `evolve.py` Step 6b 时，subprocess 只返回 return code；`ctx['wiki_stable_ready']` 永远是 0 或 -1——**精确计数丢了**。

**修法**：
- `tools/wiki_stability.py` 加 `--json`：stdout 输出结构化 JSON（`{total, tiers: {ready_stable, maturing, pre_draft, already_stable}, ready: [...], ...}`），人类报告改走 stderr。
- `tools/evolve.py` 的 `step6b_wiki_stability()` 改用 `subprocess.run(capture_output=True)`，解析 JSON 取 `tiers.ready_stable`，stderr 透传给用户看。

**效果**：
```
━━━ Summary ━━━
  wiki_stable_ready: 0     ← 现在真的是 ready 计数（当前 0，因无真机回执）
```

当未来有 wiki 页累积够 2 条日期小节，这个值会跳到实际数，`--strict` CI 也能正确 block。

### 7.2 · `tests/test_common.py` — 首次给 `_common.py` 加测试

**问题**：Wave 5 抽 `tools/_common.py` 时没写测试。parse_frontmatter 是 4 次 copy 凝出的共享库，**下次再出 bug 只能靠 case 反证**——不够工程。

**修法**：新建 `tests/`，写 `test_common.py`：
- 极简 runner，**不用 pytest**（遵循 Ascend-Forge "纯 stdlib" 原则）
- 24 条 assert 覆盖 9 个场景：
  - inline comment 剥离（`status: pending   # note` → `pending`）
  - **URL fragment 保护**（`link: https://a.com/d#section-3` 完整保留——Wave 3 的真实 bug 回归测试）
  - multi-line block list（`sources:\n  - a\n  - b` → `["a", "b"]`）
  - inline list `[a, b]`
  - 空 / 半开 frontmatter 返回 `{}`
  - `strip_frontmatter` 正反向
  - `iter_cases` yield 形态
  - `ROOT` 指向仓库根（有 `tools/` 和 `rules/ACTIVE.md`）
  - `FRONTMATTER_RE` 的正反匹配

**跑法 / 结果**：
```
$ python3 tests/test_common.py -v
=== test_common.py ===
  ✅ FRONTMATTER_RE: 能匹配标准 frontmatter
  ...（略）
通过 24 · 失败 0
✅ 全部通过
```

**设计决定**：
- **不**进 `evolve.py` 流水线——测试应在 `tests/` 独立跑，工程标准约定；如果进了 orchestrator，失败时 evolve 会 exit != 0 影响下游。
- **不**装 pytest——`python3 tests/test_common.py` 一行跑完，零依赖。
- 测试数达到 ~40+ 再评估是否加测试运行器（目前只有 24 条，够用）。

### 7.3 · `memory/pitfalls/pitfall-tool-name-vs-intent-verb.md`

**问题**：Wave 6 bench 81.2% 卡在 6 条失败题上，但**没沉淀**为 memory。pitfall 只停留在 "Wave 6 case 里的几段话" 级别，下次其他 agent 来看到 bench 失败时找不到前人的思考。

**修法**：写 pitfall memory，结构：
- 现象 + 4 条具体 bench 失败例子
- 根因 3 层（"提到 X"vs"用 X 做 Y" 区分 / 无负向 / 无时间因果）
- 缓解策略 A / B / C（加权关键词 / 意图前缀规则 / 语义路由），**明确说 C 才是真解**
- 给 bench.py 的诚实结论（**81.2% 是关键词 bag 上限，不是主 agent 水平**）
- 给主 agent 的操作提示（识别 `<工具名> 的 <x>` 模式后按意图路由）

**交叉引用**：
- `cases/2026-04-21-wave6.md`
- `memory/lessons/lesson-architecture-critique.md` #4
- `tools/bench.py` + `bench/golden-questions.yaml` q21/q23/q27/q29/q30/q31

同时更新 `memory/INDEX.md` 加了这一行。

## 反思

### 做得好的

1. **三件事都是"闭环"而不是"新功能"**：Wave 5 抽了 `_common` 但没测试，Wave 6 加了 `wiki_stability` 但精度丢，Wave 6 有 bench pitfall 但没 memory 化。Wave 7 把这三个"缺口"补上了，每个都是**前一 Wave 承诺但未交付**的东西。**这才是"持续改进"的正确定义**——不是一直加新东西，而是把之前开的口子封上。

2. **测试的"零依赖" 决策**：一开始本能想 `pytest`，但停下来问了一句"本项目真的需要 pytest 吗？" 答案是"没必要，现在 24 条 assert 完全够"。**工具选择的自律比工具选择本身更重要**。

3. **pitfall memory 的诚实结尾**：直接写"bench.py 的 81.2% 不是主 agent 的水平"——而不是含糊留白。这让未来读者不会把 bench 分数误当 KPI。

### 做得不够的

1. **`wiki_stability.py` 里有一处代码重复残留**：`promote_to_stable()` 函数还在（Wave 6 版），但 main() 里现在是内联实现（为了路由日志到 stderr）。Helper 和内联逻辑并存是**技术债的种子**。下一 Wave 应该把它清理掉——要么删 helper，要么让 helper 接受 `log_stream` 参数。

2. **测试没有覆盖 `_common.py` 之外的工具**：`bench.py` 的 `parse_yaml_simple`、`promote.py` 的 section-end 检测、`seed_from_machine.py` 的 bad_markers 过滤——都没有 unit test。**全栈覆盖率接近 0**；Wave 7 只覆盖了 1 个文件。不过这是合理的——先从被重用最多的（_common.py 被 5 工具共享）开始。

3. **`wiki_stability.py --json` 的 schema 没写文档**：stdout JSON 结构只有 evolve.py 代码里在用；要让下游（CI / 其他工具）接入，得有 schema。TODO 留给 Wave 8。

### 关于"持续重构"的再一次校准

Wave 5 我说过"重构必须跟着已发生的痛走"。Wave 7 的三件事再次验证这一条：
- `--json` 闭环是因为**我们自己看到 `wiki_stable_ready: 0` 时不确定是"真的 0"还是"丢了"**（痛点）
- 测试是因为**`_common.py` 抽出后再次修改时心里没底**（潜在痛点提前处理）
- pitfall memory 是因为**Wave 6 的 6 条失败题如果不写下来会"失忆"**（知识漂白的痛点）

**所有重构都先指向一个可观察的痛**，不做 "感觉应该重构" 类工作。
