# Wave 8：技术债闭环 + 小组目标对齐反思

## 背景

Wave 7 末尾留了 3 条 tech debt：
1. `wiki_stability.py` 里 `promote_to_stable()` helper 和 main() 内联逻辑并存
2. `bench.py::parse_yaml_simple` 零测试（又一个手写 YAML parser）
3. 测试数过了 40+，该加聚合 runner

本 Wave 把这 3 个**已知但没闭合**的口子封上；收尾时**小组突然发来"一个大脑、四层记忆、5 天→0-1 天"目标**，于是在最后加了一大段**架构对齐反思**——这才是本 Wave 最重要的部分。

## 做了什么

### 8.1 · `wiki_stability.py` helper/内联去重

**问题**：Wave 6 写 `promote_to_stable()` 函数，Wave 7 为了路由日志到 stderr 在 main() 里内联了同样逻辑。helper 没用上，但还在文件里——**两份几乎一样的 regex 替换代码**。

**修法**：
- `promote_to_stable()` 加 `log_stream` 参数（默认 stdout）
- main() 删掉内联的 `re.subn(...)` 块，改成 `promote_to_stable(path, dry_run=not args.apply, log_stream=sys.stderr if args.json else sys.stdout)`
- 测试三种模式：默认、`--json`（stdout=JSON）、`--json 2>/dev/null`（stderr 人类报告）都正常

净变化：-18 行（删了内联副本），+6 行参数化。单源逻辑恢复。

### 8.2 · `tests/test_bench_parser.py`（23 条 assert）

**问题**：`_common.py::parse_frontmatter` 有 24 条 test（Wave 7 加），但 `bench.py::parse_yaml_simple` 是**第二个手写 YAML parser**，零覆盖。Wave 6 扩 golden 集时曾静默丢题过一次，就是因为此 parser 的 `^\s{4,}` 缩进硬门槛。

**修法**：新建 `tests/test_bench_parser.py`，8 个测试函数 / 23 条 assert：
- 顶层 key 过滤（meta/version 丢弃，只保留 questions）
- 2 题标准 case
- quoted scalar（单双引号剥）
- inline list（tags: [a, b]）
- 注释 + 空行跳过
- 空输入安全（空串 / 只有 questions: / 无 questions key）
- **indent-threshold 现状记录测试**（2 空格会丢字段，4 空格 OK——**这是活文档**，以后谁改阈值会看到）
- 真实 `bench/golden-questions.yaml` 能整份解析且每题有 id/question/expected_subagent

**踩了坑**：我第一版测试写成 `q["expected"]`，结果全挂——真实 schema 是 `expected_subagent`。**这一次踩坑本身证明了 test 的价值**：测试把"我以为的 schema"和"真实 schema"的差异当场捕到。

### 8.3 · `tests/run_all.py` 聚合 runner

**问题**：Wave 7 说"测试数 ~40+ 再评估运行器"。Wave 8 过了（24 + 23 = 47）。

**修法**：30 行 runner，glob `tests/test_*.py` 自动发现，`subprocess.call` 单独跑每一份。传 `-v` 透传。继续**不依赖 pytest**。

**为什么不直接上 pytest**：单文件仍能独立跑（`python3 tests/test_common.py`），runner 只是**汇总入口**。Ascend-Forge 要装到客户笔记本上，少一个依赖就少一种"在客户机器上装失败"的可能。

### 8.4 · 小组目标对齐反思（本 Wave 的真正价值）

Wave 8 进行中时收到小组讨论记录。核心：

> 一个大脑，四层记忆 · 通过任务沉淀**可复制的方案/脚本** · 迁移 5 天 → 0-1 天 ·
> 场景 1：平台 → 客户现场；场景 2：现场 → 平台复现

**对照现状的诚实盘点**（写进 `lesson-architecture-critique.md` 的 #11/#12/#13）：

| 四层记忆 | 映射 | 当前状态 |
|---|---|---|
| L1 工作记忆 | 会话 session | ✅ |
| L2 情景记忆 | cases + memory/lessons,pitfalls | ✅ 7 cases / 4 memory atoms |
| L3 语义记忆 | wiki + memory/facts | 🟡 24 页但多 draft |
| **L4 程序记忆（可执行方案）** | skills + tools | ❌ **skills 为 0** |

**结论**：我们建的是一个**只会回忆、不会动手**的大脑。小组说的"5 天 → 0-1 天"提速**必然来自 L4**（脚本），而这一层骨架 Wave 1-7 做完还是空的。这是一个**方向性差距**，不是"工程卫生"差距。

**产出**：

## 反思

### 做得好的

1. **Wave 8.1/8.2/8.3 三件都是"说过要做的"**：没开新坑，全是闭环。和 Wave 7 一样的节奏——**Wave 的价值不是加新功能，而是把承诺封上**。

2. **test 踩到 schema 误解**（`expected` vs `expected_subagent`）：**这种 test 的失败本身就是产物**。如果没测试，下次改 bench.py 时我还会写错字段名，而且可能静默通过。

3. **对小组目标的反应**：没含糊"大致符合"，而是把"我们的 skills/ 目录是空的"这个事实**量化点出**。L4 空 = 方向性问题，不是边际改进。把这点写进 critique 而不是只写进 case，因为 critique 是**跨 Wave 可看的仪表盘**，case 会被下一轮冲下去。

4. **R034 不是拍脑袋**：先识别到痛（#11），再想两个应对（软/硬），评估软承诺已经失败过（Wave 1-7 都没产 skill），才提硬规则。**规则生效的前提是先证明软版本不工作**。

### 做得不够的

1. **没真产 skill**：Wave 8 把"没 skill"这个问题识别得很清楚，但本 Wave 没**顺手**做一个示范 skill（比如 `skills/wiki-consolidate-draft-to-stable/` 壳子，现成的 `wiki_stability.py` 工具都写好了）。这等于"指出了缺口还没填"。建议 Wave 9 第一件事就是补这一个，验证 `case_to_skill.py` 的产出形态。

2. **R034 的 evidence 只有 2 条**：还缺 1 条才能 auto-promote。坦诚留着——等下一次真实任务"本应强制但没强制"出现，作为 evidence #3（见 proposal 里的说明）。

3. **bench_parser 测试的 indent-2sp case 是"记录现状"不是"验证好设计"**：这种测试有价值但也有风险——测试用来固化了一个 quirk。如果真有一天想修 parser 允许 2 空格缩进，这条测试会阻碍正面改动。折中：测试名字叫 "indent-2sp: ... 丢失（记录现状）"，消息里明说"如果这条开始 fail，说明有人改了 indent 阈值，好事"。

### 对"持续重构跟着痛走"原则的再次校准

Wave 5/6/7/8 都是同一招：**发现痛 → 闭环 → 反思**。但 Wave 8 出现了一个新情况：**小组目标定义的痛（L4 空）和我一直自我感知的痛（工程卫生）不是同一个维度**。

这是个教训：**一个"看起来在持续改进"的 Agent，也可能一直在错误的维度上改进**。Wave 1-7 的痛都是"代码质量"层，小组要的痛是"产品效用"层。**没有外部反馈，自我反思会收敛到自己能看到的缺点**，而不是真正重要的缺点。

所以 Wave 9 的第一件事不是技术选型，是**把 L4 补起来**——哪怕只 1 个 skill，也是向"会动手的大脑"迈出的第一步。
